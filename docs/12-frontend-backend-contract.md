# 12 — Frontend / Backend Contract

Maps every dynamic frontend feature to its API operation (from `08`) and defines the UI states around each. The typed client is generated by `orval` from `openapi.yaml`, so request/response types are shared automatically; this doc fixes behaviour (loading/empty/error/optimistic/caching).

## UI state conventions

### Loading
- Lists/tables → `Skeleton` rows matching final layout (prevents layout shift).
- Overview → skeleton arch + placeholder cards.
- Route-level `loading.tsx` for first navigation; React Query `isPending` for refetch within a page.

### Empty
- `EmptyState` with a primary action (e.g. guests empty → "Add your first guest"; events empty → onboarding CTA).

### Error
- Field errors from `400` `error.fields` → bound to form inputs via react-hook-form.
- Resource errors → `ErrorState` with retry (re-runs the query).
- `401` anywhere → clear session, redirect `/login?next=<path>`.
- `403` → "You don't have access" (role) without leaking data.
- `404` on an event-scoped resource → treat as not-found/not-owned; route to `/app` with a notice.
- Toast for mutation failures that aren't field-level.

### Optimistic updates
Apply optimistic cache updates + rollback on error for high-frequency, low-risk mutations:
- Task done toggle, task add/remove, schedule reorder, section reorder, section visibility toggle, guest select/group.
Non-optimistic (await server): publish/unpublish, payments, deletes of significant data, RSVP submission.

### Caching / invalidation (React Query)
- Query keys scoped by `eventId` (e.g. `['overview', eventId]`, `['guests', eventId, filters]`).
- Mutations invalidate related keys: guest/RSVP/task/schedule changes → invalidate `['overview', eventId]` (readiness/journey/segments are computed from them).
- `staleTime` modest for live-ish data (overview, guests), longer for catalog (templates/packages).
- Prefetch overview + events in the server layout for `/app`.

### Auth expiration
- 401 interceptor in the fetch wrapper triggers a single redirect to login preserving `next`.
- Refresh-token flow (if used) transparently retries once before redirecting.

### Public invitation specifics
- No session; token in path. `GET /invite/{token}` is cacheable/ISR-friendly for the static shell; RSVP/wish are client mutations.
- RSVP form prefilled from `guest` personalisation when the token is per-guest; success shows confirmation state (no optimistic — must confirm server acceptance before cutoff rules).

## Contract source of truth

`api/openapi.yaml` is authoritative. Frontend runs `orval` to regenerate typed hooks on contract change. CI fails if generated client is out of date (`orval --check` or git-diff gate). Shared zod schemas in `lib/validation` mirror server validation for instant client feedback; the server remains the enforcing authority.
